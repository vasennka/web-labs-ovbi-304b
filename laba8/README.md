## Задание 1. Как работает ProgressBar

1. `useState(0)` хранит текущий процент.
2. `useEffect(..., [speed, isDone])` запускает `setInterval`, который каждые `speed` мс
   вызывает `setValue(prev => Math.min(prev + 1, 100))`.
3. Эффект возвращает **функцию очистки** `clearInterval` — React вызовет её при
   размонтировании и перед повторным запуском эффекта. Без неё останутся «мёртвые»
   таймеры (в React 18 StrictMode эффект специально выполняется дважды — с очисткой
   это безопасно).
4. Когда `value === 100`, `isDone === true`: эффект не создаёт новый интервал,
   выводится «Готово!» и кнопка «Заново», которая сбрасывает состояние в 0.
5. Ширина полосы: `style={{ width: `${value}%` }}` — данные, а не верстка,
   поэтому inline-стиль здесь уместнее CSS-класса.

## Задание 3 (письменный ответ). Чем отличаются периодический опрос, long polling и WebSocket? Когда использовать SSE?

**1. Периодический опрос (polling / `setInterval` + `fetch`).**
Клиент по таймеру (у нас — каждые 2 секунды) спрашивает «есть новое?» независимо от того,
есть ли новости. Плюсы: проще всего, работает везде, никаких особых протоколов.
Минусы: задержка до одного интервала; лишние запросы (в DevTools видно, что при отсутствии
новостей всё равно уходит по 30 запросов в минуту с каждой вкладки); на каждый запрос
сервер тратит заголовки, парсинг и ресурсы; плохо масштабируется.

**2. Long polling (Comet).**
Клиент делает запрос, сервер **держит его открытым** и отвечает только когда появляется
новое сообщение (или по таймауту, у нас 25 с). Получив ответ, клиент немедленно открывает
следующий запрос. Плюсы: работает через обычный HTTP (нет проблем с прокси и файрволами),
новости приходят **мгновенно**, «пустых» запросов нет. Минусы: на сервере висит по одному
открытому соединению на клиента (в Node это дешёво, но в классических «поток-на-запрос»
серверах — дорого); после ответа всегда есть «зазор» на новый запрос, в который может
попасть сообщение; сложнее балансировка и таймауты; при реконнекте легко потерять или
продублировать события (у нас решается параметром `lastId`).

**3. WebSocket.**
Один раз выполняется HTTP-«рукопожатие» с заголовком `Upgrade: websocket`, после чего
соединение остаётся открытым и данные идут в **обе стороны** кадрами с минимальными
накладными расходами (2–14 байт заголовка). Плюсы: минимальная задержка, реально
двусторонний канал, нет HTTP-оверхеда на каждое сообщение. Минусы: нужен пакет `ws`
(или другой сервер), свой протокол поверх — нужно самим реализовывать переподключение,
`ping/pong`, авторизацию и контроль доступа; некоторые прокси и корпоративные сети
режут `ws://` (отсюда fallback и библиотеки вроде Socket.IO).

**Сравнение в одну таблицу**

| | Задержка | Запросов при простое | Направление | Сложность |
|---|---|---|---|---|
| Периодический опрос | до интервала | много | клиент → сервер (ответ) | низкая |
| Long polling | мгновенно | 1 висящий запрос | клиент → сервер (ответ) | средняя |
| WebSocket | мгновенно | 0 (1 соединение) | **оба** | высокая |
| SSE | мгновенно | 0 (1 соединение) | только сервер → клиент | низкая |

**Когда вместо них достаточно Server-Sent Events.**
SSE — односторонний поток «сервер → клиент» поверх обычного HTTP с
`Content-Type: text/event-stream`. Браузер сам держит соединение, сам переподключается
и умеет досылать `Last-Event-ID`, поэтому не нужно писать свой reconnect.
Использовать SSE вместо опроса/long polling имеет смысл, когда:
* данные идут **только от сервера**: лента новостей, тикеры/курсы, прогресс длинной
  операции, уведомления, мониторинг — то, что у нас реализовано в `/sse.html`;
* нужен самый простой код без библиотек (нативный `EventSource`);
* важна совместимость с корпоративными сетями и HTTP/1.1-прокси, где WebSocket может
  блокироваться (SSE — обычный HTTP, работает поверх HTTP/2);
* обратный канал уже есть или не нужен: клиент всё равно отправляет данные обычным
  `fetch`/POST (как на нашей странице).

SSE не подходит, когда нужен **двусторонний** обмен с низкой задержкой (чаты, игры,
совместное редактирование, биржевое ядро) — там WebSocket; и когда нужен бинарный
протокол — SSE передаёт только текст UTF-8.

## Задание 2. На что смотреть в DevTools → Network

1. Открыть `/ajax.html` в двух вкладках, отправить сообщение в первой — оно появится
   во второй (задержка до 2 с).
2. В Network при пустом списке видно постоянные `GET /api/messages` каждые 2 секунды —
   это и есть цена периодического опроса.
3. На `/poll.html` запрос `GET /api/poll` **висит** в состоянии `pending`, пока не
   появится сообщение; количество запросов равно количеству сообщений (плюс таймауты).
4. На `/ws.html` в Network есть один запрос `101 Switching Protocols`, дальше в кадре
   WebSocket видны сообщения — новых HTTP-запросов нет.
