## 1. Что такое слоистая архитектура backend-сервиса

Плохой вариант, который пишут в начале: один файл `server.js`, где в обработчике
маршрута сразу лежит SQL-запрос, валидация и генерация HTML. Такой сервис работает
ровно до первой правки: изменение таблицы ломает вёрстку, а смена библиотеки для
внешнего API тянет за собой переписывание половины обработчиков.

Слоистая архитектура разбивает приложение на **слои с односторонними зависимостями**:

```
┌───────────────────────────────────────────────────────────┐
│ presentation   HTTP, маршруты, контроллеры, шаблоны        │
├───────────────────────────────────────────────────────────┤
│ application    сценарии использования (сервисы) + порты    │
├───────────────────────────────────────────────────────────┤
│ domain         сущности, правила, доменные ошибки          │
└───────────────────────────────────────────────────────────┘
        ▲                                  ▲
        │ реализует порты                  │ реализует порты
┌───────────────────────────────────────────────────────────┐
│ infrastructure  БД, внешние API, почта, файлы, кеш         │
└───────────────────────────────────────────────────────────┘
```

Ключевое правило: **зависимости направлены внутрь**. `domain` не знает ни о чём;
`application` знает только `domain`; `infrastructure` и `presentation` знают
`application`, но не наоборот. Стрелка от `infrastructure` к `application` — это
не импорт «сверху вниз», а **реализация интерфейса**: инфраструктура подставляется
в сервис извне (инверсия зависимостей, DIP).

### Как это выглядит в коде проекта

Сервис новостей ничего не знает о базе данных — он работает с портом:

```js
// application/services/NewsService.js
class NewsService {
    constructor({ newsRepository }) {          // ← абстракция, не JsonDatabase
        this.newsRepository = newsRepository;
    }

    async getBySlug(slug) {
        const news = await this.newsRepository.findBySlug(slug);
        if (!news) throw new NotFoundError('Новость');   // ← доменная ошибка
        return news;
    }
}
```

Конкретную реализацию выбирает **composition root** — единственное место, где
разрешено знать обо всём сразу:

```js
// container.js
const db = await createAppDatabase(config);                 // json ИЛИ sqlite
const newsRepository = new NewsRepositoryAdapter({ db });   // адаптер
const newsService = new NewsService({ newsRepository });    // внедрение зависимости
```

Проверка на практике: в проекте достаточно поменять `DATA_DRIVER=json` на
`DATA_DRIVER=sqlite`, чтобы вся система перешла на `node:sqlite`. Ни сервисы, ни
контроллеры, ни шаблоны при этом не меняются — смоук-тест (28 проверок) проходит
на обоих драйверах без правок.

## 2. Слои подробнее

### 2.1. Domain (ядро)

Сущности и правила, которые существуют независимо от HTTP и хранения:

```js
// domain/entities/News.js
function validateNews(input = {}, { partial = false } = {}) {
    const errors = {};
    const data = {};
    const title = String(input.title ?? '').trim();
    if (title.length < 3) errors.title = 'Заголовок должен быть не короче 3 символов';
    else data.title = title;
    // ... excerpt, content, tags, slug, publishedAt
    if (Object.keys(errors).length > 0) {
        throw new ValidationError('Проверьте поля новости', errors);
    }
    return data;
}
```

Почему это выгодно: правило «заголовок от 3 символов» описано **один раз** и
применяется и в REST API, и в админке, и в серверных страницах. Нет дублирования
между фронтендом и бэкендом, а ошибки по полям возвращаются структурированно
(`details`), из-за чего форма может подсветить конкретный input.

Доменные ошибки (`AppError`, `ValidationError`, `NotFoundError`, `AuthError`,
`RateLimitError`, `ExternalServiceError`) несут HTTP-код, но сам домен про HTTP
ничего не знает и не импортирует Express.

### 2.2. Application (сценарии использования + порты)

Сервис отвечает на вопрос «что делает система», а не «как это хранится»:

| Сервис | Сценарии |
|---|---|
| `NewsService` | список с пагинацией/фильтром, чтение по slug, создание, правка, удаление, уникальный slug |
| `GalleryService` | список по категориям, загрузка работы, удаление |
| `ContactService` | приём сообщения, валидация, сохранение, уведомление администратора, отметка «прочитано» |
| `AuthService` | вход, смена пароля, создание администратора |
| `AboutService` | текст «О нас» + сборка данных из внешних сервисов с деградацией |
| `RateLimiter` | ограничение частоты (вход, форма обратной связи) |

Порты (`application/ports/*`) — это интерфейсы: `NewsRepository`, `GalleryRepository`,
`MessageRepository`, `UserRepository`, `SettingsRepository`, `PasswordHasher`,
`VcsStatsProvider`, `WeatherProvider`, `Mailer`. Они описывают **что** нужно сервису,
но не **как** это устроено внутри.

### 2.3. Infrastructure (адаптеры)

* `JsonDatabase` — файл `db.json`: коллекции, автоинкремент id, атомарная запись
  (временный файл + `rename`) и очередь записи, чтобы параллельные запросы не затирали
  друг друга.
* `SqliteDatabase` — тот же контракт на `node:sqlite`: таблица на коллекцию, документ
  в JSON-колонке, WAL-режим.
* Адаптеры репозиториев (`adapters.js`) добавляют специфику: поиск по slug, фильтр по
  тегу/категории, сортировка по дате. «Общая» механика (пагинация, CRUD) — в базовом
  `CollectionRepository`.
* Интеграции: `GitHubStatsProvider` (официальный SDK `@octokit/rest`) и
  `WeatherProvider` (свой клиент над `fetch` с `AbortController`), общий `TtlCache`.
* `ConsoleMailer` (порт `Mailer`) и `BcryptHasher` (порт `PasswordHasher`).

Честное замечание для защиты: фильтрация и сортировка в этих адаптерах выполняются
в JavaScript после чтения коллекции. Для учебного проекта (десятки записей) это
нормально, но в продакшене фильтры уезжают в SQL (`WHERE`/`ORDER BY`/`LIMIT`) —
иначе на миллионе записей всё окажется в памяти.

### 2.4. Presentation (HTTP и MVC)

Тонкие контроллеры: только извлечь данные из запроса, вызвать сервис, выбрать ответ.

```js
// presentation/controllers/api/news.controller.js
const getNews = (newsService) => asyncHandler(async (req, res) => {
    const news = await newsService.getBySlug(req.params.slug);
    ok(res, { news });
});
```

Цепочка MVC в проекте: **маршрут → контроллер → модель (сервис + сущность) →
представление** (шаблон EJS либо React-компонент). `asyncHandler` — важная деталь:
Express 4 не передаёт ошибку из `async`-функции в error-middleware автоматически,
поэтому без обёртки отклонённый промис «подвесил» бы запрос.

Единый обработчик ошибок превращает доменные ошибки в HTTP:

```js
const status = err instanceof AppError ? err.status : 500;
// 400 ValidationError · 401 AuthError · 404 NotFoundError · 429 RateLimitError · 502 ExternalServiceError
```

## 3. Границы и инверсия зависимостей

Где проходят границы в проекте:

1. **Граница приложения и storage.** Сервис знает только метод `findBySlug`. Заменить
   JSON на Postgres = написать ещё один адаптер того же контракта.
2. **Граница приложения и внешнего мира.** Сервис говорит «дай статистику репозитория».
   Реализация может быть Octokit, GitLab, кэш или заглушка в тестах.
3. **Граница presentation и application.** Контроллеры не содержат бизнес-правил; в них
   нет ни одного обращения к базе. Всё, что можно протестировать без сервера, живёт в
   `domain` и `application`.
4. **Граница «два фронта, одна логика».** REST API для React и серверные страницы EJS
   вызывают одни и те же сервисы, поэтому поведение и валидация совпадают.

Зачем инверсия зависимостей (DIP) — если коротко, три причины:
* **заменяемость** инфраструктуры (файл ↔ SQLite, GitHub ↔ заглушка);
* **тестируемость** (не нужно поднимать базу и сеть, чтобы проверить правило);
* **направление зависимостей** — код бизнес-логики не «прибит» к фреймворку, поэтому
  смена Express на Fastify затронет только `presentation`.

## 4. REST API в проекте

| Метод и путь | Назначение | Коды ответов |
|---|---|---|
| `GET /api/v1/health` | работоспособность, драйвер БД, uptime | 200 |
| `GET /api/v1/news?page&limit&tag&search` | список новостей | 200, 400 |
| `GET /api/v1/news/:slug` | одна новость | 200, 404 |
| `GET /api/v1/news-latest?limit` | свежие новости для главной | 200 |
| `GET /api/v1/gallery?page&limit&category` | работы галереи | 200, 400 |
| `GET /api/v1/gallery/:id` | одна работа | 200, 404 |
| `POST /api/v1/contact` | приём сообщения формы | 201, 400, 429 |
| `GET /api/v1/about` | текст «О нас», контакты | 200 |
| `GET /api/v1/integrations` | данные сторонних сервисов | 200 |

Принципы, которые реализованы (и о которых стоит сказать на защите):

* **ресурсы, а не действия**: в URL существительные во множественном числе, действие
  выражается HTTP-методом (`GET`/`POST`);
* **коды ответов по смыслу**: `201 Created` при создании сообщения, `400` с деталями по
  полям, `404` для отсутствующего slug, `429` при спаме, `502` для упавшего внешнего API;
* **единый формат ответа**: `{ ok: true, ... }` или `{ ok: false, error, code, details }`;
* **пагинация в метаданных**: `{ items, total, page, limit, pages }` — клиент знает,
  есть ли следующая страница, и не выпрашивает «всё сразу»;
* **версионирование через URL**: основной префикс `/api/v1`; роутер смонтирован и на
  `/api`, где отдаётся заголовок `Deprecation` и `Link rel="successor-version"` —
  так клиенты могут переезжать постепенно;
* **идемпотентность**: `GET` ничего не меняет; `DELETE` повторный вернёт 404, а не
  «удалит дважды»; создание сообщения дублируется только по явному действию пользователя
  (кнопка блокируется на время запроса);
* **валидация на сервере** — источник истины, клиентская проверка только для удобства.

О сравнении с GraphQL и gRPC (для полноты темы №3): GraphQL удобен, когда у клиентов
очень разные потребности в выборке полей (и реализует архитектурный паттерн
«единая точка входа + резолверы», то есть тот же MVC на уровне схемы); gRPC уместен
для внутренних межсервисных вызовов, где важны контракт, строгая типизация и
производительность бинарного протокола. Для публичного сайта с 9 эндпоинтами REST
проще и дешевле: он кэшируется по URL, отлаживается в браузере и не требует
дополнительного слоя.

## 5. Монолит или микросервисы: какой ценой

Проект — **монолит с чёткими внутренними границами**. Обоснование:

| Критерий | Монолит (наш случай) | Микросервисы |
|---|---|---|
| Транзакции | ACID «из коробки»: сообщение сохранилось — увидели в админке | распределённые транзакции/SAGA, вся сложность на разработчике |
| Развёртывание | один процесс, один конфиг | оркестратор, service discovery, конфиги по сервисам |
| Отладка | один лог и один стек вызовов | распределённая трассировка обязательна |
| Масштабирование | вертикальное + несколько экземпляров | независимое по сервисам |
| Размер команды | 1–5 человек | десятки, отдельные команды на сервис |

Микросервисы оправданы, когда команда большая и разные части системы имеют сильно
разный профиль нагрузки. Цена: сетевые ошибки в каждом вызове, согласованность данных
становится задачей приложения, отладка превращается в охоту за корреляционными id.
Мы выбрали монолит, но **слои построены так, что их можно «вынуть»**: `presentation`
уже отделён от `application`, а `application` общается через порты — если когда-нибудь
понадобится вынести сервис интеграций в отдельный процесс, менять придётся только адаптер.

## 6. Что даёт такая архитектура на защите (короткие ответы)

* **Где живёт бизнес-логика?** В `application/services`; в контроллерах её нет.
* **Как поменять базу?** Написать адаптер с тем же контрактом и подставить в `container.js`.
* **Как проверить логику без сервера?** Импортировать сущность/сервис и вызвать метод:
  в `domain` нет зависимостей, в `application` — только порты.
* **Почему ошибки — классы, а не строки?** По типу выбирается HTTP-код и текст для
  пользователя в одном месте (`errorHandler`), незнакомые ошибки пробрасываются.
* **Почему два фронта (React и EJS)?** Требования ТЗ: React на фронте и шаблонизатор для
  представлений. Оба используют одни сервисы, поэтому не расходятся в поведении.
* **Минусы решения?** Больше файлов и уровень абстракций; для маленького сайта это
  избыточно; нужно дисциплинированно не «протаскивать» SQL и `req` в сервисы.
