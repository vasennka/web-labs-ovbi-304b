# Проект «Фотостудия PRISMA» (тема 25)

Учебный проект: сайт фотостудии с публичной частью, галереей, новостями,
формой обратной связи и админкой, закрытой паролем.

Стек: **Node.js + Express + EJS** (бэкенд и админка) и **React + Vite** (SPA публичной части).

---

## 1. Как запустить

```powershell
# из папки project

# 1) зависимости (бэкенд + фронтенд)
npm run install:all

# 2) наполнить базу начальными данными (админ, новости, галерея)
npm --prefix backend run seed

# 3) собрать React-приложение
npm run build

# 4) запустить сервер (он же раздаёт собранный React и серверные страницы)
npm start
```

Открыть в браузере:

| Адрес | Что это |
|---|---|
| http://127.0.0.1:4000/ | Публичная часть на **React** (SPA): главная, галерея, новости, о студии, контакты |
| http://127.0.0.1:4000/site/ | Та же публичная часть, отрисованная на сервере **шаблонизатором EJS** |
| http://127.0.0.1:4000/admin/login | **Админка** (закрыта паролем) |
| http://127.0.0.1:4000/api/v1/news | **REST API** |

Логин админки по умолчанию — `admin`, пароль — `admin123` (задаётся в `.env`,
см. `backend/.env.example`). **После входа смените пароль** на дашборде.

### Полезные команды

```powershell
npm run dev            # одновременно бэкенд (nodemon-режим) и Vite-dev (порт 5173)
npm --prefix backend run smoke   # автотест всего стека: 28 проверок API, EJS, админки, CSRF
```

Смена хранилища с файла на SQLite — одна переменная окружения:

```powershell
$env:DATA_DRIVER="sqlite"; npm --prefix backend run seed; npm start
```

### React в режиме разработки (hot reload)

```powershell
npm --prefix frontend run dev      # http://localhost:5173
# Vite проксирует /api и /uploads на http://127.0.0.1:4000 (см. frontend/vite.config.js)
```

## 3. Обоснование архитектуры

**Выбрано: чистая (луковая) архитектура с элементами MVC в слое представления.**
Фактически это «луковица» из четырёх колец, где зависимости направлены строго внутрь:

```
presentation  →  application  →  domain
      ↑                ↑
infrastructure ───────┘   (реализует порты, объявленные в application)
```

Правило зависимостей: `domain` не знает ни о чём, `application` знает только про
`domain`, `infrastructure` и `presentation` зависят от `application`, но не наоборот.
Сервис `NewsService` вызывает `newsRepository.list()` — то есть интерфейс, а не
`JsonDatabase`. Кто именно подставит реализацию, решает `container.js`.

**Что это даёт на практике (это видно прямо в коде проекта):**

1. **Хранилище заменяется одной строкой.** `DATA_DRIVER=sqlite` — и вместо JSON-файла
   работает `node:sqlite`. Сервисы, контроллеры, шаблоны и React при этом не изменены.
   Оба драйвера проходят один и тот же смоук-тест (28/28).
2. **Внешние сервисы изолированы.** Бизнес-логика просит «статистику репозитория» и
   «погоду» у портов `VcsStatsProvider` и `WeatherProvider`. Подменить GitHub на GitLab
   или настоящий Octokit на заглушку в тестах — это правка `container.js`, а не сервиса.
3. **Тестируемость.** Ядро (`domain`) не имеет зависимостей: валидацию новости можно
   проверить одной строкой, без запуска сервера и без базы. Смоук-тест поднимает
   приложение на отдельном порту и с отдельной базой — это возможно потому, что
   зависимости внедряются, а не импортируются жёстко.
4. **Ошибки в одном месте.** Домен кидает `ValidationError` / `NotFoundError` /
   `AuthError`, а `presentation/middleware/errorHandler.js` превращает их в HTTP-коды
   (400 / 404 / 401) и в JSON для API либо в HTML для страниц. Контроллеры не занимаются
   обработкой ошибок вовсе.
5. **Одна логика — два интерфейса.** REST API (для React) и серверные страницы (EJS)
   вызывают одни и те же сервисы. Именно поэтому на сайте есть две версии одних и тех же
   страниц, и обе всегда согласованы между собой.

**Плюсы выбранного подхода:** независимость бизнес-логики от фреймворка и БД;
возможность менять драйвер БД и внешние сервисы без переписывания кода; понятное
расположение кода для нового разработчика; лёгкое тестирование.
**Цена (честно):** больше файлов и «лишний» слой абстракций для маленького сайта;
придётся объяснять, зачем нужны интерфейсы; чуть выше порог входа.

**MVC внутри presentation.** Маршруты (`routers`) → контроллеры (`controllers`) →
модель (сервисы + сущности) → представление (`views` для EJS или React для SPA).
Такое разделение описано в теме доклада №1: классическая MVC-цепочка, где «модель»
живёт в `domain`+`application`, а «представление» может быть двумя разными.

**Почему не хардкорный Clean Architecture «в лоб»** (с отдельными интерфейсами-файлами
на каждый порт и value-объектами): для учебного сайта это дало бы больше церемоний, чем
пользы. Мы сохранили главное — направление зависимостей и порты, — но оставили
структуру читаемой.

## 4. Обоснование выбора шаблонизатора

**Выбран EJS.** Сравнение вариантов, которые обычно рассматривают:

| Шаблонизатор | Плюсы | Минусы в нашем случае |
|---|---|---|
| **EJS** ✅ | Это обычный HTML + вставки `<%= %>`; дизайнер/преподаватель может читать шаблон как вёрстку; поддержка `include` для шапки и подвала; никакой новой грамматики (кроме знакомого по лабам JavaScript); работает с любой структурой, легко вставить EJS-фрагмент в React-страницу; минимальный оверхед | Легко случайно написать логику в шаблоне — нужно следить (у нас логика в сервисах) |
| Pug (Jade) | Компактная запись без закрывающих тегов | Собственный синтаксис и отступы; не HTML; передать верстку между людьми сложнее; при переносе в React всё равно нужен HTML |
| Handlebars | Logic-less, безопасный по умолчанию | Любое условие сложнее `if` требует хелпера; для админских форм это неудобно |
| Nunjucks | Мощный (наследование, макросы) | Синтаксис ближе к Jinja/Python — изучать заново, избыточно для ~15 страниц |
| React SSR | Единый стек с SPA | Полноценный SSR для админки — оверинжиниринг: сборка, стриминг, гидратация |

EJS покрывает то, для чего он нужен, и хорошо сочетается с React: SPA отвечает за
интерактивные страницы, а EJS — за **админку и серверные версии публичных страниц**.
Для админки это особенно уместно: обычные HTML-формы + POST + редирект работают даже
без JavaScript, а защита (сессия + CSRF) не требует CORS.

Где EJS используется в проекте:

* `presentation/views/admin/*` — вся админка: форма входа, дашборд, списки, формы правки,
  обратная связь, раздел «О нас»;
* `presentation/views/site/*` — серверные версии публичных страниц (`/site/...`), включая
  форму обратной связи, работающую без JavaScript;
* `presentation/views/partials/*` — шапка и подвал с навигацией (общие для админки и сайта).

## 5. Сторонние сервисы (интеграции)

Требование ТЗ выполнено **двумя** способами — чтобы показать оба подхода.

### 5.1. Официальный SDK: GitHub через `@octokit/rest`

* Файл: `backend/src/infrastructure/integrations/GitHubStatsProvider.js`
* Что показывает на сайте: звёзды, форки, открытые issues, дату последнего push
  и ссылку на репозиторий (страница «О студии», виджет «GitHub»).
* Почему SDK, а не «ручной» запрос: SDK сам следит за версией API и заголовками,
  корректно работает с лимитами и повторами, не нужно вручную собирать URL и парсить ответ.
* Ленивый `import('@octokit/rest')` — приложение запустится, даже если библиотека
  не установлена (тогда виджет честно скажет «сервис недоступен»).

### 5.2. Клиент поверх сетевой библиотеки: Open-Meteo через `fetch`

* Файл: `backend/src/infrastructure/integrations/WeatherProvider.js`
* Что показывает: температуру, ветер и расшифровку кода погоды WMO для Москвы.
* Технические детали: `AbortController` с таймаутом 5 с; явная проверка `response.ok`
  (fetch НЕ бросает исключение на 404/500); `clearTimeout` в `finally`.
* Сервис выбран потому, что **не требует API-ключа** — проект запускается без регистрации.

### 5.3. Устойчивость (это важная часть защиты)

* Оба ответа кэшируются в `TtlCache` на 10 минут — не дёргаем чужое API на каждый запрос.
* Если сервис недоступен, возвращается последнее удачное значение (`stale: true`),
  а если его нет — заглушка с `degraded: true` и текстом ошибки.
* Страница «О студии» и API `/api/v1/integrations` в любом случае отдают **200 OK**:
  падение чужого сервиса не должно ломать наш сайт.

## 6. Самодельные контролы на фронте

Требование «один контрол сделать самому» выполнено дважды — оба написаны без сторонних
библиотек.

### 6.1. `<Carousel />` — карусель галереи (`frontend/src/components/ui/Carousel.jsx`)

Как работает:

1. **Состояние.** `index` — номер текущего слайда, `dragX` — текущий сдвиг при
   перетаскивании (в пикселях), `paused` — приостановлена ли автопрокрутка.
2. **Сдвиг ленты.** Слайды лежат в flex-контейнере, который перемещается через
   `transform: translateX(calc(-index * 100% + ${dragX}px))`. Плавность задаёт CSS-transition;
   во время перетаскивания transition отключается, иначе лента «догоняла» бы палец с задержкой.
3. **Перетаскивание.** Используются Pointer Events — один код и для мыши, и для пальца,
   и для стилуса: `pointerdown` → `setPointerCapture` (чтобы события шли к нам, даже если
   курсор вышел за границы) → `pointermove` считает дельту → `pointerup` решает, листать
   или вернуть слайд на место. Порог: сдвиг больше 15% ширины или «щелчок» быстрее 0.5 px/мс.
4. **Автопрокрутка.** `useEffect` с `setInterval`, зависящий от `[autoPlayMs, paused, count, index]`:
   при смене слайда таймер перезапускается, поэтому пользователю всегда достаётся полный
   интервал на просмотр. Функция очистки `clearInterval` обязательна (в React 18 StrictMode
   эффект выполняется дважды — иначе получили бы два таймера).
5. **Клавиатура и доступность.** Контейнер `tabIndex={0}`, обработка `←/→/Home/End`.
   `role="region"`, `aria-roledescription="carousel"`, `aria-live="polite"` только у активного
   слайда (чтобы скринридер не перечитывал все картинки), у точек — `role="tab"` и `aria-selected`.
6. **Мелочи UX.** Клик по слайду после перетаскивания подавляется (`onClickCapture`
   с проверкой пройденного пути), пауза при наведении и фокусе, кнопка «пауза/включить авто»,
   счётчик «3 / 8» и полоса прогресса.

### 6.2. `<StarRating />` — оценка сайта звёздами (`frontend/src/components/ui/StarRating.jsx`)

* Реализован по ARIA-паттерну **radiogroup**: `role="radiogroup"` на контейнере,
  `role="radio"` + `aria-checked` на каждой звезде.
* **Roving tabindex**: в порядке табуляции участвует только активная звезда (`tabIndex=0`),
  остальные `-1`. Пользователь не «пробегает» пять остановок Tab, но ходит стрелками
  `←/→`, а `Home/End` выбирают крайние значения.
* **Hover-предпросмотр** не меняет значение: при наведении показывается предварительная
  оценка, а значение фиксируется только кликом. Повторный клик по выбранной звезде — сброс.
* Скрытый `<input type="hidden" name="rating">` делает контрол совместимым с обычной
  HTML-формой.
* Значение проверяется на сервере (1–5, целое) — клиентская валидация никогда не считается доверенной.

## 8. Безопасность (кратко, подробнее — в докладе)

* пароли — только bcrypt-хеш (`BcryptHasher`), проверка — `bcrypt.compare`;
* сессия в cookie `httpOnly` + `sameSite=lax`, `session.regenerate()` после входа
  (защита от session fixation);
* CSRF: токен в сессии + скрытое поле формы + `timingSafeEqual` при сравнении;
* ограничение частоты: вход (5 попыток / 5 мин) и форма обратной связи (10 / 5 мин);
* загрузка файлов: белый список MIME, лимит 4 МБ, имя файла генерируется (защита от
  path traversal и «двойных расширений»), каталог отдаётся как статика;
* `helmet` + CSP, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`;
* валидация входных данных — на сервере (доменные сущности), клиентская — лишь подсказка;
* React вставляет текст только через `{value}` (никакого `dangerouslySetInnerHTML`) —
  защита от XSS; в EJS — `<%= %>`, а не `<%- %>`, для пользовательских данных.
