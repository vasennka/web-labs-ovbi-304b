# Доклад №2. Архитектура backend-сервиса с REST API

**Что разбирается:** слоистая архитектура (controller → service → repository),
гексагональная архитектура и Clean Architecture, где проходят границы и зачем нужна
инверсия зависимостей. Монолит против микросервисов — какой ценой.

> Эта же тема разобрана во втором документе с привязкой к коду проекта:
> **`project/DOKLAD.md`** (§3 «Границы и инверсия зависимостей», §4 «REST API», §5 «Монолит
> или микросервисы»). Здесь — общее изложение темы, без привязки к конкретному проекту.

## 1. Отправная точка: как выглядит «код без архитектуры»

```js
app.post('/news', async (req, res) => {
  const { title, content } = req.body;
  if (!title || title.length < 3) return res.status(400).send('Плохой заголовок');
  await pool.query('INSERT INTO news SET ?', { title, content });   // SQL прямо здесь
  await fetch('https://api.telegram.org/...');                      // внешний сервис прямо здесь
  res.send('ok');                                                   // ответ прямо здесь
});
```

Проблемы предсказуемы:

* **правило проверки заголовка** продублируется в API, админке, импорте из CSV — и рано или поздно разъедется;
* **сменить БД** = переписать обработчики;
* **внешний сервис упал** — падает и создание новости, потому что уведомление не отделено от бизнес-операции;
* **протестировать** нельзя: чтобы проверить правило, надо поднять HTTP, базу и сеть.

## 2. Слоистая архитектура: controller → service → repository

Первый и самый распространённый шаг — разделить ответственности на слои:

```
HTTP-запрос
   ▼
controller     только HTTP: разобрать ввод, выбрать код ответа   (framework-specific)
   ▼
service        бизнес-правила: «что должно произойти»            (framework-agnostic)
   ▼
repository     доступ к данным: «как это сохранить/прочитать»     (SQL/ORM/файл)
   ▼
БД
```

| Слой | Знает про | Не знает про |
|---|---|---|
| Controller | HTTP, request/response, коды | SQL, детали бизнес-правил |
| Service | домен, правила, транзакции | `req`/`res`, конкретную БД |
| Repository | SQL/ORM/файл, маппинг | HTTP и бизнес-правила |

Плюс: код предсказуем, правило валидации описано в одном месте, сервис тестируется
без HTTP и без базы (подставляем фейковый репозиторий).

Минус: **репозиторий протекает**. Как только сервису нужно «дай страницу отсортированную
по дате с фильтром», в интерфейс репозитория попадают `orderBy`, `offset`, `limit` —
то есть SQL-терминология. Это нормально, но напоминает: абстракция — не самоцель.

## 3. Гексагональная архитектура (порты и адаптеры, Alistair Cockburn, 2005)

Идея: **ядро приложения в центре**, вокруг — интерфейсы (порты), а реализации (адаптеры)
подключаются снаружи. Ядро ничего не знает ни о базе, ни о HTTP, ни о фреймворке.

```
        ┌────────────── адаптеры ──────────────┐
        │  REST-контроллер   CLI   cron/queue   │
        └───────────────┬──────────────────────┘
             порт "вход" │  (что приложение умеет)
        ┌───────────────▼──────────────────────┐
        │            ЯДРО (domain)             │
        │  сущности + правила + сервисы        │
        └───────────────┬──────────────────────┘
             порт "выход"│  (что приложению нужно)
        ┌───────────────▼──────────────────────┐
        │  Postgres-адаптер, SMTP, внешний API  │
        └──────────────────────────────────────┘
```

* **Порт** — это интерфейс (в JS — неявный контракт или абстрактный класс с JSDoc).
* **Адаптер** — реализация: Postgres, файл, HTTP-клиент, заглушка для тестов.
* Направление зависимостей строго внутрь: адаптеры зависят от ядра, ядро — ни от чего.

## 4. Clean Architecture (Robert Martin) и «луковый» вариант

Дальше ту же мысль формализовали в виде «луковицы» слоёв:

```
Frameworks & Drivers  ←  Interface Adapters  ←  Use Cases  ←  Entities
        (Express)          (controllers,          (сервисы)     (правила
                            gateways)                            бизнеса)
                  зависимости направлены ВНУТРЬ
```

* **Entities** — правила, которые не изменятся, даже если завтра уберут веб-интерфейс.
* **Use Cases** — сценарии приложения («создать новость», «принять сообщение»).
* **Interface Adapters** — превращают данные «снаружи» в формат ядра (и обратно).
* **Frameworks & Drivers** — Express, драйвер БД, SDK внешнего сервиса.

Правило зависимостей одно и то же: **ни одна внутренняя стрелка не должна импортировать
внешнюю**. Если use case импортирует Express — это уже не Clean Architecture.

Разница с гексагоном — больше терминологическая: гексагон говорит «порты и адаптеры»,
Clean — «слои с правилом зависимостей». По сути оба про одно: **ядро независимо от деталей**.

## 5. Зачем инверсия зависимостей (DIP) — на примере

Без DIP сервис сам создаёт зависимость:

```js
class NewsService {
    constructor() {
        this.repo = new PostgresNewsRepository();   // жёсткая связь
    }
}
```

Что плохо: сервис знает про Postgres; в тестах нужна настоящая база; смена хранилища —
правка сервиса.

С DIP зависимость передаётся снаружи:

```js
class NewsService {
    constructor({ newsRepository }) {               // зависит от абстракции
        this.newsRepository = newsRepository;
    }
}

// composition root — единственное место, где известны конкретные классы:
const repo = config.driver === 'sqlite'
    ? new SqliteNewsRepository({ db })
    : new FileNewsRepository({ db });
const newsService = new NewsService({ newsRepository: repo });
```

Выгода: смена хранилища — одна строка в composition root; тесты подставляют фейк;
ядро остаётся неизменным. Именно этот приём в проекте позволяет работать и с файлом,
и с SQLite, ничего не меняя в сервисах.

## 6. Где проходят границы (важнейшая часть для защиты)

1. **Граница HTTP.** Всё, что знает про `req`/`res`, обязано остаться в контроллере.
2. **Граница транзакции.** Транзакцией управляет сервис (или шина), а не репозиторий:
   «сохранить заказ и списать товар» — это один use case, а не два независимых вызова.
3. **Граница внешнего мира.** Вызовы чужих API — за портом. Иначе недоступность Telegram
   ломает бизнес-операцию, а тесты требуют интернета.
4. **Граница форматов.** DTO (что пришло по сети) ≠ сущность (что хранится) ≠ view-model
   (что показываем). Их смешивание приводит к утечке внутренних полей наружу.

## 7. Монолит или микросервисы

| Критерий | Монолит | Микросервисы |
|---|---|---|
| Транзакции | ACID «из коробки» | SAGA, eventual consistency, компенсации |
| Развёртывание | один процесс/образ | оркестратор, service discovery, версии контрактов |
| Отладка | один лог, один стек | распределённая трассировка, correlation id |
| Изоляция сбоев | падение затрагивает всё приложение | ограничена сервисом |
| Масштабирование | вертикальное или копии целиком | по каждому сервису отдельно |
| Стоимость изменений контракта | рефакторинг внутри репозитория | версионирование API + координация команд |
| Команда | 1–10 человек | desyatki+, отдельная команда на сервис |

Практическое правило: **монолит по умолчанию, микросервисы — по обоснованной необходимости**
(разные профили нагрузки, независимые релизные циклы, требования изоляции данных).
Правильно построенный монолит с портами и явными границами «распиливается» на сервисы
постепенно: например, интеграции выносятся в отдельный процесс, а адаптер в монолите
начинает ходить к нему по HTTP.

## 8. Как понять, что архитектура «поехала»

Признаки деградации, которые полезно искать глазами:

* контроллер больше 50 строк, в нём есть `if` про бизнес-смысл;
* сервис импортирует `express` или `pg`/`mysql` напрямую;
* сущность знает про JSON-сериализацию или про HTTP-код;
* один и тот же `fetch` чужого API в трёх местах;
* тест «на создание сущности» поднимает сервер и базу.

Хороший ориентир: **любой класс, кроме контроллера, должен импортироваться и работать
в обычном `node -e`** без веб-сервера.

## 9. Мини-выводы

* Слои отвечают на вопрос «кто за что отвечает», порты/адаптеры — «куда направлены зависимости».
* Clean Architecture = слоистая архитектура + правило зависимостей (все стрелки внутрь)
  + инверсия зависимостей в точках подключения инфраструктуры.
* DIP окупается на второй-третьей замене реализации: другая БД, другой внешний сервис,
  тесты с фейками.
* Микросервисы — не «следующий уровень», а другой набор компромиссов: цена — распределённость.
