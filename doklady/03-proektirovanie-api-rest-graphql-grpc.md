# Доклад №3. Проектирование API: REST, GraphQL, gRPC

**Что разбирается:** уровни зрелости REST, версионирование, идемпотентность, коды ответов,
пагинация. Что такое GraphQL и какой архитектурный паттерн он реализует. Где уместен gRPC.

---

## 1. REST: не «JSON по HTTP», а архитектурный стиль

REST (Representational State Transfer, Roy Fielding, 2000) — набор ограничений:

1. **Клиент-сервер** — интерфейс отделён от хранилища.
2. **Отсутствие состояния (stateless)** — каждый запрос самодостаточен: всё нужное для
   обработки приходит в запросе (включая токен/сессию). Сервер не помнит «прошлый шаг».
3. **Кэшируемость** — ответ помечается как кэшируемый или нет (`Cache-Control`, `ETag`).
4. **Единообразие интерфейса** — ресурсы в URL, действия через HTTP-методы и коды.
5. **Слои** — между клиентом и сервером могут быть прокси и шлюзы, о которых клиент не знает.
6. **Code on demand** (необязательно) — сервер может отдавать исполняемый код (JS-клиент).

Нарушения, которые встречаются чаще всего:
`GET /getNewsById?id=5` (глагол в URL), `POST /news/delete/5` (действие вместо метода),
«умный» сервер, который держит контекст между запросами (ломает масштабирование).

## 2. Уровни зрелости REST (модель Ричардсона)

| Уровень | Что это | Пример |
|---|---|---|
| **0. «Один туннель»** | один эндпоинт, всё через тело | `POST /api` + `{action: "createNews"}` |
| **1. Ресурсы** | разные URL для разных сущностей | `POST /news`, `GET /news/5` |
| **2. HTTP-методы и коды** | VERB + статусы, кэш-заголовки | `DELETE /news/5 → 204` |
| **3. HATEOAS** | ответы содержат ссылки на возможные переходы | `{id:5, _links:{delete:"/news/5"}}` |

Большинство «REST API» в реальности — уровень 2. Уровень 3 (HATEOAS) красив в теории,
но на практике почти не используется: клиенты и так знают структуру API, а ссылки
раздувают ответы. Уровень 0 и 1 — признак того, что API проектировали «как получилось».

## 3. Методы, идемпотентность и безопасность

| Метод | Безопасный (не меняет данные) | Идемпотентный (повтор = тот же результат) | Кэшируемый |
|---|---|---|---|
| GET | да | да | да |
| HEAD | да | да | да |
| PUT | нет | **да** | нет |
| PATCH | нет | нет (зависит от операции) | нет |
| DELETE | нет | **да** | нет |
| POST | нет | **нет** — создаёт новый ресурс каждый раз | нет |

Зачем это важно на практике: мобильный клиент потерял сеть и повторил `PUT /news/5` —
ничего не сломалось. А повторный `POST /orders` создаст второй заказ — поэтому для
платежей и заказов применяют **Idempotency-Key** (клиент генерирует uuid, сервер
запоминает результат и на повтор отдаёт его же).

## 4. Коды ответов: минимальный разумный набор

| Код | Когда |
|---|---|
| 200/201/204 | успех / создано / успех без тела |
| 304 | не изменилось (при `If-None-Match`) |
| 400 | ошибка формата/валидации запроса |
| 401 / 403 | не аутентифицирован / аутентифицирован, но нет прав |
| 404 | ресурса нет |
| 409 | конфликт (уникальность, версия ресурса) |
| 422 | данные синтаксически верны, но семантически недопустимы |
| 429 | лимит частоты (обязательно вернуть `Retry-After`) |
| 500 / 502 / 503 | ошибка сервера / плохой шлюз (чужой сервис) / недоступность |

Ошибки стоит отдавать **машиночитаемо и с деталями по полям**:

```json
{
  "ok": false,
  "error": "Проверьте поля формы",
  "code": "VALIDATION_ERROR",
  "details": { "email": "Некорректный e-mail", "message": "Минимум 10 символов" }
}
```

Тогда фронтенд подсвечивает конкретные поля, а не показывает одну строку «ошибка».

## 5. Версионирование

Варианты и их компромиссы:

| Способ | Пример | Плюсы | Минусы |
|---|---|---|---|
| URL-версия | `/api/v1/news` | просто, видно в логах, легко кэшировать | URL «некрасивый», ресурс как будто другой |
| Заголовок | `Accept: application/vnd.api+json;v=2` | чистые URL | сложнее тестировать «руками» |
| Параметр | `?api-version=2` | гибко | легко забыть, плохо кэшируется |
| Без версий, только эволюция | добавление полей, не удаляя старых | минимум ломки клиентов | требует дисциплины |

Практическое правило: **добавлять поля можно всегда, удалять и менять типы — только с новой
версией**. Для перехода используют «алиас»: старый путь продолжает работать, но отвечает
заголовками `Deprecation: true` и `Link: </api/v2/news>; rel="successor-version"` (так
сделано в проекте для `/api`).

## 6. Пагинация и фильтрация

| Вид | Пример | Особенности |
|---|---|---|
| Offset/limit | `?page=3&limit=20` | просто; «плавает» при вставках (элементы сдвигаются) |
| Cursor (keyset) | `?after=eyJpZCI6MTIzfQ&limit=20` | стабильно, быстро по индексу; нельзя прыгнуть на «страницу 7» |
| Link-заголовки | `Link: <...>; rel="next"` | REST-стиль, клиент не конструирует URL сам |

Ответ всегда должен содержать метаданные — иначе клиент не знает, есть ли ещё данные:

```json
{ "items": [...], "total": 42, "page": 2, "limit": 10, "pages": 5 }
```

Фильтры — через query: `?category=студия&tag=печать&search=свет`. Мощные фильтры
(`where[price][gte]=1000`) выглядят «умно», но превращаются в SQL по частям запроса —
это прямой путь к инъекциям и утечкам.

## 7. GraphQL: что это и какой паттерн реализует

GraphQL — это **язык запросов к схеме** и рантайм для его исполнения (Facebook, 2015).

Клиент сам описывает, какие поля ему нужны:

```graphql
query {
  news(limit: 3) {
    title
    publishedAt
    author { name }
  }
}
```

Отличия от REST:

| | REST | GraphQL |
|---|---|---|
| Эндпоинты | много (`/news`, `/news/:id`, `/gallery`) | один (`POST /graphql`) |
| Кто решает, что вернуть | сервер | **клиент** (выбор полей) |
| Over-fetching / under-fetching | обычное дело | решается самим запросом |
| Кэширование | по URL «из коробки» | нужен persist/нормализация (Apollo, urql) |
| Сложность сервера | ниже | выше: схема, резолверы, N+1, лимиты глубины |
| Файлы/загрузка | нативно | нужно расширение/отдельный путь |

**Какой архитектурный паттерн реализует GraphQL.** Транспорт у него один, а схема играет роль
**фасада (Front Controller)** над доменом: запрос разбирается, сопоставляется со схемой и
попадает в **резолверы** — по сути это те же контроллеры, только привязанные не к URL-пути,
а к полю схемы. То есть GraphQL = «единая точка входа + маршрутизация по схеме + слой
преобразования данных (Data Mapper)». Внутри резолвера ровно та же пирамида
`resolver → service → repository`, что и в REST-контроллере, — меняется только «вход».

Классические грабли GraphQL: проблема N+1 (решается DataLoader-батчингом), дорогие
глубокие запросы (нужны ограничения сложности и глубины), отказ от HTTP-кэша
(нужен persist-кэш на клиенте).

## 8. gRPC: где уместен

gRPC — фреймворк удалённого вызова процедур от Google: HTTP/2 + Protocol Buffers
(бинарная схема) + генерация клиентов и серверов из `.proto`.

Сильные стороны: строгий контракт, компактный быстрый бинарный формат, стриминг
(клиентский, серверный, двунаправленный), мультиплексирование в одном соединении,
мёртвые линии (deadlines) и коды ошибок «из коробки».

Где уместен:

* **межсервисные вызовы** внутри микросервисной архитектуры (низкая задержка, высокая частота);
* **стриминг** телеметрии, логов, чатов;
* **сгенерированные клиенты** для многих языков (Go, Java, Python, C#, JS);
* **мобильные клиенты** там, где важен трафик и батарея.

Где не стоит: публичный API для браузера напрямую (gRPC требует HTTP/2-трейлеров и не
работает из браузера без grpc-web-прокси), простые CRUD-сайты, интеграция с внешними
партнёрами «по документации» (им проще REST+JSON).

## 9. Как выбрать

```
Публичное API, разные клиенты, отладка браузером, кэш по URL   → REST
У одного клиента много разных экранов/выборок полей, мобильные   → GraphQL
Внутренние сервисы, высокая частота, стриминг, строгий контракт → gRPC
```
Часто их **комбинируют**: наружу REST (проще для партнёров и кэша), между сервисами gRPC,
а GraphQL — как фасад для собственных клиентов со сложными выборками.

## 10. Мини-выводы

* REST — это ограничения (stateless, единообразие, кэш), а не «вернуть JSON».
* Идемпотентность определяет, можно ли безопасно повторить запрос при обрыве сети.
* Версионировать надо изменения контракта, а не каждый релиз; переход — через алиасы и Deprecation.
* GraphQL решает over/under-fetching ценой усложнения сервера и кэша; внутри — те же
  сервисы и репозитории.
* gRPC — инструмент для внутренних быстрых и стриминговых взаимодействий.
