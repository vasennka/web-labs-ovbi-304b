# Доклад №1. Паттерны организации клиентского кода: MVC, MVP, MVVM

**Что разбирается:** откуда пришли паттерны, чем реально отличаются, где живёт состояние
в каждом из них, и что из этого дожило до React.

---

## 1. Зачем вообще паттерны

Любой интерфейс делает три вещи: **хранит данные**, **показывает их** и **реагирует на действия
пользователя**. Пока кода мало, всё это пишется в одном файле. Проблемы начинаются, когда:

* состояние (что введено, что загружено, что выбрано) лежит в десятке мест и рассинхронизируется;
* логика «покажи/скрой/посчитай» перемешана с работой DOM;
* тестировать можно только кликами в браузере.

Паттерны MVC, MVP и MVVM — три разных ответа на вопрос **«как разделить данные, представление
и логику представления и как связать их между собой»**.

## 2. MVC — Model–View–Controller (1979, Smalltalk-80)

Исторически первый паттерн. Появился в Smalltalk-80 применительно к оконным приложениям,
позже переехал в серверную разработку (Rails, Django, ASP.NET MVC) и в браузер.

```
Пользователь ──► Controller ──► Model
                    │             │
                    ▼             │ изменение модели
                  View ◄──────────┘ (View читает модель)
```

* **Model** — данные и правила их изменения.
* **View** — отрисовка: читает модель и показывает её. «Глупое» представление.
* **Controller** — принимает ввод (клик, отправку формы), меняет модель.

Ключевое в классическом MVC: **View подписывается на изменения Model** (наблюдатель),
а Controller лишь меняет модель. Модель не знает ни о View, ни о Controller.

**В браузере проблема.** В веб-версии классический MVC стал «односторонним»:
`Controller → Model → View`, а View — это шаблон (HTML-строка). Так работает серверный MVC
(и наш проект: маршрут → контроллер → сервис → шаблон EJS). Но в клиентском коде, где DOM
уже загружен, кто-то должен синхронизировать модель со страницей — и эту работу в MVC
не зафиксировали. Отсюда путаница и «толстые контроллеры», которые лезут в DOM.

## 3. MVP — Model–View–Presenter (начало 1990-х, Taligent; популярно в Android и GWT)

Идея: убрать из View любую логику и передать её посреднику — презентеру.

```
View ◄──(интерфейс)──► Presenter ──► Model
   пассивная              ▲
                          └── View вызывает методы презентера
```

* **View** — «тупое» представление. Сообщает презентеру о событиях: `loginButtonClicked()`,
  `onTextChanged(text)` — и умеет только `showError()`, `setLoading(true)`, `renderList(data)`.
* **Presenter** — вся логика представления: решает, что делать в ответ на событие, держит
  ссылку на View **через интерфейс**, меняет модель.
* **Model** — данные.

Ключевое отличие: View **не наблюдает** за моделью, связь организует Presenter (двусторонняя,
но явная). Взаимодействие идёт через интерфейс View, поэтому презентер тестируется без браузера:

```js
class LoginPresenter {
    constructor(view, authService) { this.view = view; this.authService = authService; }

    async onLoginClicked(login, password) {
        this.view.setLoading(true);
        try {
            await this.authService.login(login, password);
            this.view.navigateTo('/admin');
        } catch (err) {
            this.view.showError(err.message);   // View — интерфейс, поэтому в тесте это заглушка
        } finally {
            this.view.setLoading(false);
        }
    }
}
```

Минус MVP: очень много «воды». На каждый чих в интерфейсе — метод в интерфейсе View
и метод в презентере. Для формы на 20 полей это сотни строк склейки.

## 4. MVVM — Model–View–ViewModel (2005, Microsoft, WPF; пришло в веб через Knockout, Vue)

Ответ на минус MVP: пусть связывание сделает фреймворк, а не разработчик.

```
View ◄──двусторонний binding──► ViewModel ──► Model
        (автоматически)
```

* **ViewModel** — модель для конкретного представления: поля, которые видит пользователь,
  и команды (методы), которые он вызывает. Не знает про DOM.
* **View** — объявляет в разметке привязки: `<input v-model="email">`, `{{ user.name }}`.
* **Binding-движок** сам синхронизирует значения туда и обратно (через наблюдателей/прокси).

Ключевое: **ViewModel не знает о View вообще** (в отличие от MVP, где презентер держит View),
а связь обеспечивает инфраструктура — `Object.defineProperty`/`Proxy`, «геттеры-сеттеры»
и подписки.

## 5. Главное отличие в одной таблице

| | MVC | MVP | MVVM |
|---|---|---|---|
| Кто держит ссылку на View | View знает модель (наблюдатель) | Presenter знает View **через интерфейс** | Никто: связывает binding-движок |
| Кто знает о DOM | View | View (и только он) | View (и только он) |
| Логика представления | частично в Controller, частично в View | целиком в Presenter | целиком в ViewModel |
| Связь | одно- или двусторонняя через модель | двусторонняя, ручная | двусторонняя, автоматическая |
| Тестируемость логики | средняя | высокая (за счёт интерфейса View) | высокая |
| Цена | «толстые» контроллеры | много склейки | нужен фреймворк с реактивностью |
| Примеры | Rails, Django, Express + EJS | Android (старый), GWT | WPF, Vue, Svelte |

**Где живёт состояние** — вопрос, который чаще всего задают на защите:

* **MVC** — в Model (и частично размазано по View: «какие вкладки открыты» часто живёт в DOM).
* **MVP** — в Presenter; View максимально «пустое».
* **MVVM** — в ViewModel как наблюдаемые поля; View — их проекция на экран.

## 6. Что из этого в современном React

React формально не MVC/MVP/MVVM. Компонент — это функция, которая возвращает **описание
интерфейса** (виртуальное дерево) по состоянию:

```
UI = f(state)
```

* состояние живёт в `useState`/`useReducer` (это ближе всего к ViewModel или к модели представления);
* роль View — сам возвращаемый JSX; он не мутирует DOM вручную;
* роль Controller/Binding выполняет сам React: сравнивает предыдущее и новое дерево
  и вносит минимальные изменения в DOM (diffing/reconciliation);
* однонаправленный поток данных: состояние → рендер → событие → новое состояние.

Мостики к классике:

* React + Redux/Zustand — это уже почти **MVVM/MV\***: стор = модель, селекторы = view-model,
  компоненты = view. Только обновление не «магическое», а через подписки.
* Серверный MVC и клиентский React отлично сосуществуют — в нашем проекте так и сделано:
  публичная часть на React, админка на MVC-шаблоне (Express → контроллер → EJS),
  а данные в обоих случаях приходят из одних и тех же сервисов.

## 7. Типичные ошибки «на практике»

1. **MVVM без фреймворка** — самодельные getters/setters и ручные подписки дают баги
   рассинхронизации. Нужна либо библиотека, либо дисциплина «одного источника правды».
2. **Смешивание слоёв** — `fetch` прямо в обработчике кнопки (в проекте это вынесено
   в `api/client.js`, а состояние загрузки — в хук `useApi`).
3. **View, который знает слишком много** — если в шаблоне появляются вычисления бизнес-логики,
   это уже не View.
4. **Controller, который лезет в DOM** — путь к «толстым» контроллерам и непроверяемому коду.

## 8. Мини-выводы

* Отличие MVP от MVC: в MVP View пассивное, и Presenter держит на него ссылку через интерфейс.
* Отличие MVVM от MVP: ViewModel не знает View, связывание автоматическое (binding).
* В React роль «синхронизатора» взял на себя рантайм, поэтому привычные паттерны
  превратились в «состояние + компонент + однонаправленный поток».
