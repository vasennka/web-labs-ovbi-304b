# Доклад №4. Аутентификация и авторизация в вебе

**Что разбирается:** cookie-сессии против JWT, где хранить токен, refresh-токены,
OAuth 2.0 и OpenID Connect «на пальцах», RBAC/ABAC.

> **Аутентификация** отвечает на вопрос «кто ты», **авторизация** — «что тебе разрешено».
> Это разные задачи, и путать их — источник половины уязвимостей.

---

## 1. Как аутентификация выглядит «под капотом»

1. **Идентификация** — пользователь называет логин.
2. **Проверка** — сервер убеждается, что он тот, за кого себя выдаёт:
   * что-то, что он **знает** (пароль, PIN);
   * что-то, что у него **есть** (TOTP-код, аппаратный ключ, смарт-карта);
   * что-то, чем он **является** (биометрия).
3. **Установление сессии** — сервер выдаёт «пропуск», который клиент предъявляет дальше.

Сервер **обязан** хранить не пароль, а его медленный хеш:

```js
// Правильно: bcrypt/argon2 со солью и cost-фактором
const hash = await bcrypt.hash(password, 10);      // ~60-100 мс на проверку — перебор дорогой
const ok = await bcrypt.compare(input, hash);

// Неправильно: md5/sha1 без соли — миллионы вариантов в секунду, радужные таблицы
```

## 2. Cookie-сессии против JWT

### Cookie-сессия (stateful)

```
1. POST /login           → сервер создаёт запись в хранилище сессий
2. Set-Cookie: sid=abc   → httpOnly, Secure, SameSite=Lax
3. Каждый запрос         → Cookie: sid=abc → сервер ищет сессию по sid
4. POST /logout          → запись удаляется, cookie гасится
```

Плюсы: мгновенный отзыв (удалили запись — доступ пропал), сессионные данные живут на сервере,
cookie можно сделать `httpOnly` (недоступна из JS — XSS её не украдёт).
Минусы: состояние на сервере (в кластере — общий стор/Redis); при кросс-доменных сценариях
нужны `SameSite=None; Secure` и CORS с credentials.

### JWT (stateless)

JWT = `header.payload.signature`, подписанный сервером (обычно HS256 или RS256).
Сервер не хранит состояние: он просто проверяет подпись и срок.

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMiLCJleHAiOjE3MzAwMDAwMDB9.подпись
└── заголовок (алгоритм)  └── полезная нагрузка (claims)        └── подпись
```

Плюсы: не требует общего стора; удобен между сервисами; подходит для мобильных клиентов.
Минусы, о которых надо говорить обязательно:

* **отозвать JWT до истечения срока нельзя** — только через чёрный список, а это уже состояние;
* payload **не зашифрован**, только подписан — секреты внутрь не кладут;
* большие токены на каждый запрос;
* классическая ошибка — разрешить алгоритм `none` или принимать `alg` из заголовка
  без проверки (подмена RS256 на HS256).

### Сравнение

| | Cookie-сессия | JWT |
|---|---|---|
| Состояние | на сервере | в токене |
| Отзыв доступа | мгновенный | сложный (short TTL + blacklist) |
| Защита от XSS | `httpOnly` cookie | зависит от места хранения |
| Защита от CSRF | нужны `SameSite`/токен | обычно менее подвержен (нет авто-отправки cookie) |
| Масштабирование | общий стор сессий | «из коробки» |
| Кросс-доменный API | сложнее | удобно |
| Где применяют | классический сайт с браузером | API для SPA-мобильных/третьих сторон |

**Вывод для нашего проекта:** браузерный сайт с админкой → **cookie-сессия**
(`httpOnly`, `sameSite=lax`, `session.regenerate()` после входа). Это даёт мгновенный выход
(сессия уничтожается) и защищает cookie от кражи через XSS. JWT здесь был бы хуже:
отзыв доступа при уходе администратора превратился бы в задачу.

## 3. Где хранить токен в браузере

| Место | Доступ из JS | Уязвим к XSS | Уязвим к CSRF |
|---|---|---|---|
| `localStorage` | да | **да** (XSS читает токен) | нет |
| `sessionStorage` | да | **да** | нет |
| cookie без `httpOnly` | да | **да** | да |
| cookie `httpOnly` + `sameSite` | **нет** | нет (кража из JS невозможна) | да → закрывается CSRF-токеном |
| память (переменная JS) | да, но сбрасывается при перезагрузке | да | нет |

Правило: **если токен доступен JavaScript — считайте, что XSS его украдёт**.
Для браузера предпочтительны `httpOnly`-cookie + CSRF-защита; для мобильных приложений —
защищённое хранилище ОС (Keychain/Keystore).

## 4. Refresh-токены и короткий срок жизни access-токена

Схема, которая закрывает главный минус JWT (невозможность отзыва):

```
Login         → access (15 мин, в памяти) + refresh (30 дней, httpOnly cookie, хранится в БД)
Каждый запрос → Authorization: Bearer <access>
Access истёк → POST /auth/refresh (cookie) → новый access (+ возможно ротация refresh)
Logout/подозрение → refresh удаляется из БД → обновить пару невозможно
```

Правила безопасности refresh-токена:

* хранить **хеш** refresh-токена в БД и привязывать к устройству/IP-семейству;
* **ротация**: при каждом обновлении выдаётся новая пара, старая инвалидируется;
* если пришёл уже использованный refresh → это признак кражи: гасим всю цепочку;
* никакого refresh в `localStorage`.

## 5. OAuth 2.0 и OpenID Connect «на пальцах»

**OAuth 2.0** — про **делегированную авторизацию**: приложение получает ограниченный
доступ к данным пользователя в другом сервисе, не зная его пароль. Это не про аутентификацию.

Роли: **Resource Owner** (пользователь), **Client** (наше приложение),
**Authorization Server** (сервер, выдающий токены), **Resource Server** (хранит данные).

Код-поток («Authorization Code» + PKCE) — основной безопасный вариант для веб/мобильных:

```
1. Браузер → /authorize?client_id=...&redirect_uri=...&scope=...&code_challenge=...
2. Пользователь видит «Приложение X просит доступ к …» и подтверждает (на домене провайдера!)
3. Провайдер → redirect_uri?code=...
4. Бэкенд обменивает code + code_verifier → access + refresh (это происходит по защищённому каналу)
5. Бэкенд запрашивает данные в Resource Server с access-токеном
```

Зачем PKCE: перехваченный `code` без `code_verifier` бесполезен — раньше в мобильных
приложениях можно было перехватить `code` через «свою» схему URL.

Чего делать **нельзя**: «implicit flow» (токен отдаётся прямо в адресной строке) — устарел,
токен попадает в историю и referrer.

**OpenID Connect (OIDC)** = OAuth 2.0 + слой идентичности: добавляет `id_token` (тот же JWT
с claims о пользователе: `sub`, `email`, `name`) и endpoint `/.well-known/openid-configuration`.
Проще говоря: **OIDC отвечает на вопрос «кто пользователь», OAuth — «что ему разрешено делать
в моём сервисе от его имени»**. Кнопка «Войти через Google» — это OIDC поверх OAuth.

## 6. Авторизация: RBAC и ABAC

**RBAC (role-based)** — права выдаются ролям, роли — пользователям:

```
admin   → news.create, news.delete, gallery.upload, users.manage
editor  → news.create, news.update, gallery.upload
viewer  → (только чтение)
```

Плюсы: просто объяснять, легко администрировать, естественно ложится на админку.
Минусы: «роль-взрыв» — как только появляются правила вида «редактор может править только
свои новости», ролей становится слишком много.

**ABAC (attribute-based)** — решение принимается по атрибутам субъекта, ресурса, действия
и контекста:

```
Правило: allow если
  subject.role == "author" AND subject.id == resource.ownerId
  OR subject.role == "admin"
  AND context.time внутри рабочих часов
```

Плюсы: гибко (время, отдел, регион, классификация данных). Минусы: сложнее отлаживать и
объяснять пользователю, нужен движок политик, риск непредсказуемых решений.

Промежуточный вариант, который чаще всего и нужен: **RBAC + владелец ресурса** («автор
может править своё»), а ABAC — когда правил действительно много (финансы, медицина, госсектор).

**Где проверять авторизацию?** Только на сервере. Скрытая кнопка в интерфейсе — не защита:
запрос можно отправить руками. Правильный порядок: аутентификация → авторизация → выполнение,
причём на каждом уровне (маршрут, сервис — если правило зависит от данных, например «свой ресурс»).

## 7. Практический чек-лист

* пароли — только медленный хеш (bcrypt/argon2/scrypt) + соль;
* сессионная cookie: `httpOnly`, `Secure`, `SameSite=Lax/Strict`;
* `session.regenerate()` после входа (защита от session fixation);
* CSRF-токен для всех «меняющих» методов + `timingSafeEqual` при сравнении;
* лимит попыток входа и задержки против перебора (например 5 попыток / 5 минут);
* одинаковая ошибка «неверный логин или пароль» — не подсказываем, что существует;
* короткий access + ротация refresh, отзыв refresh при выходе;
* единый ответ для «нет прав» (не раскрываем существование ресурса);
* логирование входов и изменений прав (у нас — событие с логином и результатом);
* 2FA для администраторов, если это не учебный проект.

## 8. Мини-выводы

* Аутентификация ≠ авторизация; проверка прав обязана быть на сервере.
* Cookie-сессия удобнее и безопаснее для браузерного сайта; JWT — для API и мобильных,
  при этом его нельзя «отозвать», поэтому нужны короткие TTL и refresh-схема.
* Хранение токена в `localStorage` — добровольная передача его XSS-атаке.
* OAuth — про доступ, OIDC — про личность поверх OAuth.
* RBAC достаточно для большинства проектов; ABAC — когда правил становится много.
