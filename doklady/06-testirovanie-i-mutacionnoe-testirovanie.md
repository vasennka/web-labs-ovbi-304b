# Доклад №6. Юнит- и мутационное тестирование в JS

**Что разбирается:** что такое юнит-тесты и мутационное тестирование, когда их можно
применять, и какова цена этих подходов.

---

## 1. Пирамида тестов: где место юнит-тестам

```
        ▲  редкие, дорогие, медленные
   E2E  │  (Playwright/Cypress: «пользователь купил товар»)
        ├─────────────────────────────────
  интеграционные (API + БД, сервис + внешний сервис-заглушка)
        ├─────────────────────────────────
   unit │  много, дешёвые, быстрые (миллисекунды)
        ▼
```

* **Юнит-тест** проверяет **одну единицу поведения** в изоляции: функцию, метод, класс —
  без сети, без базы, без файловой системы, без времени «сейчас».
* Интеграционный тест проверяет стык: сервис + реальная БД, контроллер + HTTP.
* E2E — весь путь через интерфейс.

Ключевая мысль: юнит-тестов должно быть больше всего, потому что они дают максимальную
скорость обратной связи за минимальные деньги.

## 2. Что делает тест хорошим

Хороший юнит-тест обладает четырьмя свойствами (акроним FIRST):

* **Fast** — миллисекунды: разработчик запускает их на каждое сохранение файла;
* **Independent** — не зависит от порядка и состояния других тестов;
* **Repeatable** — одинаковый результат локально и в CI, без сети и без «сегодня»;
* **Self-validating** — сам сообщает «прошёл/упал», без чтения логов глазами.

Структура теста — «AAA»:

```js
test('calculateAverage считает средний балл', () => {
    // Arrange — подготовка
    const data = [{ name: 'A', score: 80 }, { name: 'B', score: 90 }];

    // Act — действие
    const result = calculateAverage(data);

    // Assert — проверка
    expect(result).toBe(85);
});
```

Правила, которые экономят месяцы:

1. **Тестировать поведение, а не реализацию.** Проверять «вернулось 85», а не «вызвался
   метод reduce». Иначе любой рефакторинг ломает тесты, и их начинают отключать.
2. **Один тест — одно утверждение по смыслу.** Если тест «проверяет всё», по падению
   непонятно, что именно сломалось.
3. **Проверять границы**: 0, пустой массив, `null`/`undefined`, отрицательные числа,
   максимальные длины, дубликаты, «почти равные» значения.
4. **Не тестировать сторонние библиотеки** — тестируйте свой код.
5. **Имена тестов — как требования**: «возвращает null для отрицательного числа»
   лучше, чем «test factorial 2».

## 3. Почему чистые функции тестировать легко, а «грязные» — тяжело

```js
// Легко: чистый прирост
function applyDiscount(price, percent) { return price - price * percent / 100; }
test('скидка 10% от 1000', () => expect(applyDiscount(1000, 10)).toBe(900));

// Тяжело: функция ходит в сеть, знает про Date.now() и пишет в файл
async function createInvoice(userId) {
    const user = await db.getUser(userId);          // база
    const number = `INV-${Date.now()}`;             // время
    await fs.writeFile(`/invoices/${number}`, ...); // файловая система
    await mailer.send(user.email, number);          // внешний сервис
}
```

Отсюда практический вывод: **тестируемость — это архитектурное свойство**.
Чтобы «тяжёлые» функции стали тестируемыми, зависимости передают снаружи (инверсия
зависимостей): репозиторий, часы (`clock.now()`), почтовый клиент — всё это параметры.
Тогда в тесте подставляются тривиальные заглушки — это и есть «seam» (шов) для теста.

Тестовые двойники (кратко):

| Вид | Что делает | Когда |
|---|---|---|
| Stub | возвращает заданное значение | «пусть getUser вернёт вот такого пользователя» |
| Spy | записывает вызовы, ничего не меняет | проверить, что `mailer.send` был вызван |
| Mock | задаёт ожидания на вызовы | когда важен именно факт/порядок вызовов |
| Fake | упрощённая рабочая реализация | in-memory репозиторий вместо БД |

Правило: если для теста нужно много моков — это сигнал, что функция делает слишком много.

## 4. Инструменты в JS

```bash
# встроенный тест-раннер Node.js (без зависимостей, Node 18+)
node --test

# Jest — популярен, много «из коробки», тяжелее
npm i -D jest

# Vitest — единый с Vite, быстрый, ESM-дружелюбный
npm i -D vitest

# покрытие
node --test --experimental-test-coverage
npx vitest run --coverage
```

Пример на встроенном раннере (работает без установки пакетов):

```js
// laba4.test.js
import test from 'node:test';
import assert from 'node:assert/strict';
import { factorial } from './laba4.js';

test('factorial: базовые случаи', () => {
    assert.equal(factorial(0), 1);
    assert.equal(factorial(1), 1);
    assert.equal(factorial(5), 120);
});

test('factorial: отрицательное число даёт null', () => {
    assert.equal(factorial(-1), null);
});

test('factorial: слишком глубоко — диапазон переполняется', () => {
    assert.throws(() => factorial(10000), RangeError);
});
```

## 5. Покрытие кода: что оно значит и чего не значит

Метрики покрытия: **строки**, **ветви** (ветки if/тернарников), **функции**,
**условия** (подвыражения).

Что важно понимать:

* **100% строк ≠ отсутствие багов.** Покрытие говорит, что код *исполнялся*,
  а не что результат *проверен*: вызов функции без единого `assert` тоже «покрывает» строки.
* Опасна погоня за метрикой: появляются тесты «для галочки», которые ничего не проверяют.
* Разумная цель для бизнес-логики: строки 70–90%, **ветви — приоритетнее** (там живут
  условия и ошибки).
* Покрытие полезно как **индикатор пробелов**: «а этот обработчик ошибок вообще тестируется?»
* Писать тесты «на объём» бессмысленно: важнее покрыть критичные сценарии
  (деньги, права доступа, расчёты).

## 6. Мутационное тестирование: проверка самих тестов

Идея: инструмент **намеренно ломает код** (мутация) и смотрит, заметят ли тесты.

Типовые мутации:

* заменить оператор: `>` → `>=`, `+` → `-`;
* изменить константу: `100` → `101`;
* убрать строку/вызов функции;
* инвертировать условие `if (x)` → `if (!x)`;
* заменить возвращаемое значение на `null`/`0`/`true`.

Результаты:

* **Killed** — тесты упали: мутация обнаружена. Хорошо.
* **Survived** — тесты прошли: **дыра в тестах** (или мёртвый код). Это и есть главный результат.
* **Timeout / error** — мутация делает код «висящим» или несовместимым.
* **No coverage** — строка не исполняется тестами вообще.

**Mutation score** = убитые / (убитые + выжившие). Практический ориентир: 60–80% уже неплохо;
100% обычно недостижимо и не нужно (эквивалентные мутации: изменение не меняет поведение).

Инструменты:

```bash
npm i -D @stryker-mutator/core @stryker-mutator/jest-runner
npx stryker run

# или быстрый вариант для Node-тестов
npx stryker run --mutate "src/**/*.js"
```

Цена:

* **медленно**: каждая мутация — прогон всего набора тестов; на большом проекте — часы;
* **требует стабильных быстрых тестов** (иначе результат шумный);
* **дорого по ресурсам**, поэтому применяют не ко всему коду, а к критичным модулям
  (расчёты, права, деньги, валидация);
* иногда даёт эквивалентные мутации, которые невозможно убить, — их приходится игнорировать
  списком исключений.

**Когда применять мутационное тестирование:**

* в проектах с высокой ценой ошибки (финансы, медицина, безопасность);
* перед крупным рефакторингом, чтобы убедиться, что тесты реально защищают поведение;
* периодически (ночные запуски в CI) для аудита качества тестов, а не на каждый коммит;
* для оценки «а не занимаемся ли мы имитацией тестирования».

**Когда не надо:** на старте проекта (сначала нужны базовые тесты), для кода-клея,
в автогенерированных участках, при нестабильных/долгих тестах.

## 7. Где тесты ставить в процессе

| Уровень | Когда запускать | Что ловится |
|---|---|---|
| pre-commit | секунды | синтаксис, форматирование, быстрые тесты изменённых файлов |
| при пуше / Pull Request | минуты | юниты + интеграционные + линтер + типы |
| nightly | десятки минут | мутационное тестирование, нагрузочные, E2E-наборы |
| перед релизом | по регламенту | полный прогон, смоук на стенде |

Принцип «сломанное окно»: если тест «иногда падает» (flaky), его надо починить или удалить
сегодня же — иначе команда привыкает игнорировать красное, и тесты перестают работать
как средство контроля.

## 8. Что покрывать в первую очередь

Приоритет по «цене ошибки × вероятности»:

1. **Деньги и расчёты** (скидки, налоги, итоги корзины).
2. **Права доступа** (кто что может: «редактор не удаляет чужие новости»).
3. **Валидация и границы** (пустые строки, максимальные длины, некорректные типы).
4. **Преобразование данных** (парсинг JSON, форматирование дат, slug).
5. **Работа с ошибками** (неизвестная ошибка не «глотается», а пробрасывается).

Что можно не покрывать юнитами: тонкие контроллеры и форматирование вывода —
их быстрее проверить одним интеграционным тестом или глазами.

## 9. Как это выглядит в нашем проекте

* **Быстрая проверка логики** — автотесты внутри лабораторных (`✔`/`✘` в консоли):
  они проверяют результат функций на граничных данных.
* **Смоук-тест проекта** (`npm --prefix backend run smoke`) — это интеграционный уровень:
  поднимается сервер на отдельном порту и с отдельной базой, проверяются REST API,
  пагинация, валидация, EJS-страницы, вход в админку, CSRF-защита и отдача SPA — 28 проверок.
* **Почему не юнит-тесты «на всё»** — при учебном объёме кода смоук-тест даёт лучшую
  отдачу на единицу усилий: он видит и архитектуру, и проводку зависимостей.
* **Что стоило бы покрыть мутационным тестированием в первую очередь**: валидацию
  новостей и доменные правила (там реально важны границы `>=`/`>`), и `RateLimiter`.

## 10. Мини-выводы

* Юнит-тест проверяет одну единицу поведения и стоит копейки; их должно быть больше всего.
* Тестируемость определяется архитектурой: чистые функции и внедрение зависимостей
  превращают «непроверяемый» код в простой.
* Покрытие — индикатор пробелов, а не доказательство корректности.
* Мутационное тестирование проверяет **сами тесты**, оно точное, но дорогое — применяют
  точечно к критичным модулям.
* Главная ценность тестов — быстрый и надёжный рефакторинг, а не «зелёная галочка в CI».
